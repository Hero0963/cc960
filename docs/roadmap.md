## 下一步

1. **驗證「車不落 b/h」能不能當結構性篩選**（最高優先——**便宜且可能省掉大量算力**）
   - 為什麼：`§8.4` 實測發現車落 b/h 路時平衡率只有 16%、不落則 62%。若這條規則夠準，就能**不用引擎**、幾微秒篩掉大部分失衡局面。
   - ⚠ 教訓：2026-07-25 曾用「首著能否打進底線」當結構篩選，結果會把**標準開局本身**篩掉。這次先確認標準開局通過（車在 a/i，通過），再全池驗一遍。
   - Done 條件：全池統計「車落 b/h」與 cp 的關聯，決定要不要做成篩選或介面提示。

2. **對值得的組合做全池評估**
   - 依 `§8.4` 的結果挑 1–2 組全跑，產出該組的平衡名單。優先「象、炮、兵」（4,272 局，以本次吞吐估約 27 小時）。
   - Done 條件：新名單併進 `BALANCED_CP`，平衡池從目前的 280 局擴大。

3. **實戰試玩**（低成本、高資訊量）

   - Done 條件：`docs/playtest.md`（新檔）記下每局編號＋一兩句感想；發現規則問題就回報成 issue。

## 已定案，不要再重開的決策

| 決策 | 理由（詳見 rationale.md） |
|------|--------------------------|
| 明置隨機開局，不做暗子 | 暗子＝揭棋的生態位，會引入運氣與隱藏資訊 |
| 不加大棋盤 | 歷史先例全數失敗；將棋證明機制比盤面關鍵 |
| 紅黑點對稱（非軸對稱） | 棋手視角的「公平相同」；且使合法池大增、將位隨機成為可能 |
| 象／兵限「預走合法步」可達點 | 保住棋味與殘局知識 |
| 將帥固定中路 | 中路自對稱最簡；將位隨機與士的宮內異位留給 v5 |
| 產生器頁維持單檔、零相依、可離線 | GitHub Pages 直接吃 `docs/index.html`；不引入框架或 bundler |
| **不做「紅黑兩邊完全不對稱」** | 公平性退化為只能逐局實測；池規模 10¹¹ 使編號與審局失效（spec.md §11） |
| **不改回軸對稱為主規格** | 同路正面相對助長兌子求和；軸對稱版保留為新手／展示池 |
| **兵維持可進一格** | 固定原位只剩 10,803 局，且進兵是結構多樣性的主要來源（spec.md §11） |
| **象的原軌道收為 5 點（v4）** | 河頭象實戰極罕見；實測對平衡率毫無影響（排除結構衝突後仍 49.4%），採用理由是**棋形更貼近棋手直觀**，不宣稱改善平衡（spec.md §1） |
| **產生器頁不提供行棋** | 定位是「開局盤面產生器」，不是線上對弈；走法引擎留給檢定與 FEN 使用 |
| **對外只用原始編號一種號碼** | 一個局面同時有原始編號與各池密集編號反而難懂；跨工具交換用 FEN，分享用 `?id=`（spec.md §3） |
| **完整版不改密集編號** | 建索引需先枚舉 52 萬，與單檔離線頁衝突（spec.md §3） |
| 賽制＝雙局換色（對抗賽）／選局選邊（單局） | 不採 ban 制：解決不了先手優勢，且會把局面推向保守（rationale.md §五） |
| 授權＝程式 MIT ＋ 文件 CC BY 4.0 | 文件與規則敘述要顯著署名；玩法本身著作權不保護 |
