## 0. 座標系與資料結構

| 項目 | 定義 |
|------|------|
| `col` | 0..8，紅方視角左→右，對應直線 **a..i** |
| `row` | 0..9，**row 0 = 紅方底線**，row 9 = 黑方底線；row 4/5 之間為河界 |
| 位置寫法 | 本檔用 `c1` 表示 col=c(2)、row=0（棋手習慣的 1-based 橫線編號）；程式內一律 `[row, col]` 0-based |
| 棋盤 | `bd[row][col]`，空點為 `null` |
| 棋子 | `{ t, c }`，`t ∈ K A B N R C P`（將士象馬車炮兵），`c ∈ 0 紅 / 1 黑` |
| 著法 | `[r, c, rr, cc]`（從 → 到） |

九宮：col 3..5，紅 row 0..2 / 黑 row 7..9。宮頂線＝紅 row 2 / 黑 row 7（炮的原始橫線）。河沿＝紅 row 4 / 黑 row 5。

子力價值（**僅供靜置檢定比較大小**，不是引擎評估值）：`R 9 > C 4.5 > N 4 > B 2 = A 2 > P 1`（`K 1000`）。

## 1. 擺法規則（6 條）

1. **走法、吃法、將軍、勝負規則完全同標準中國象棋**，只有初始擺放不同。
2. **紅黑點對稱**：黑方擺法 ＝ 紅方旋轉 180°，即紅方 `(r, c)` 的子，黑方對應在 `(9−r, 8−c)`。
   從各自座位看，雙方陣形一模一樣（紅「一路」兵進 ↔ 黑「1路」卒進，**不是同一 column**）。
3. **將帥固定中路九宮底線（e1/e10），雙士固定貼於兩側（d1/f1）**。中路自對稱，且中路必有兵卒相隔，永不照面。
4. **象 2 子**隨機置於「原軌道」7 點中任 2 點：

   | 分區 | 點（紅方） | `[row, col]` |
   |------|-----------|--------------|
   | 底線 | c1, g1 | `[0,2] [0,6]` |
   | 宮頂線 | a3, e3, i3 | `[2,0] [2,4] [2,8]` |
   | 河沿 | c5, g5 | `[4,2] [4,6]` |

   象若不在底線，該底線位**留空**（不補其他子）。
5. **馬 2 子、車 2 子**隨機分配「剩餘的底線非九宮路」（a,b,c,g,h,i 扣掉被底線象占用者）；
   **炮 2 子**隨機置於宮頂線任 2 路（9 路取 2），**不可疊上宮頂線的象**。
6. **兵 5 子**在 a,c,e,g,i 五路，各路獨立取「原位（row 3）」或「前進一格（row 4）」，**不可疊上河沿的象**。

### 設計原則：「預走合法步」

象與兵的所有可能起始位置，都必須是「開局前在己方領土走**原本合法步**」可以到達的點。
變的是出發陣形，不變的是每個子的本性——因此棋味、手筋與殘局知識完整保留。
（象走田字且不過河 → 從 c1/g1 出發可達的己方點正好是那 7 點；兵只能直進 → 原位或進一格。）

## 2. 首著靜置檢定

擺法合法只是必要條件，還要通過檢定才進入合法池。目的：**剔除「開局就有一方能白吃大子」的失衡局面**。

```
若 開局照面 或 任一方開局被將  → 不合法（why: facing / check）
對 雙方 的每個「合法的首著吃子」(r,c)→(rr,cc)：
    有根且不虧 ＝ 吃完後該格會被對方攻擊，且 VAL[被吃子] ≤ VAL[出手子]
    對稱可回應 ＝ 吃完後，對方在點對稱位置 (9−r,8−c)→(9−rr,8−cc) 仍能走同型子吃回同型子
                   （且該著不自將）
    若 兩者皆不成立 → 不合法（why: 被攻擊時 winning-capture，否則 free-capture）
全部通過 → 合法
```

**為什麼「對稱可回應」算平衡**：點對稱下紅的襲擊與黑的對應襲擊發生在**對角相反的兩處**，互不干擾——紅吃一子，黑照樣吃回同型子，淨值為零，只是把局面變尖銳而非失衡。

實作見 `src/setup.js` 的 `quietStartCheck()`。效能上只生「吃子著法」再個別驗自將（`legalCaptures()`），比全合法著法快一個量級。

## 3. 編號系統

每個開局有一個唯一整數編號（類似 Chess960 的 position number）。採**混合基數**：

```
id = OFFSETS[象位組] + ((馬idx × rBase + 車idx) × 36 + 炮idx) × 32 + 兵遮罩
```

| 欄位 | 基數 | 說明 |
|------|------|------|
| 象位組 | 21 | C(7,2)，7 個原軌道點取 2；各組大小不同，故用 `OFFSETS` 前綴和定位 |
| 馬 idx | C(m,2) | m ＝ 扣掉底線象位後、底線剩餘可用路數（4、5 或 6） |
| 車 idx | C(m−2,2) | 馬占掉 2 路後剩餘路取 2（`rBase`） |
| 炮 idx | 36 | C(9,2)，宮頂線 9 路取 2，字典序 |
| 兵遮罩 | 32 | 5 bit，bit i = 1 表示第 i 路（a,c,e,g,i）進一格 |

**編號空間**

| 象位組型態 | 組數 | m | 每組大小 | 小計 |
|-----------|------|---|---------|------|
| 兩象都在底線 {c1,g1} | 1 | 4 | 6×1×36×32 = 6,912 | 6,912 |
| 一象在底線 | 10 | 5 | 10×3×36×32 = 34,560 | 345,600 |
| 兩象都不在底線 | 10 | 6 | 15×6×36×32 = 103,680 | 1,036,800 |
| **合計 `RAW_TOTAL`** | 21 | | | **1,389,312** |

編號空間包含「結構衝突」（炮或進兵疊上象位）的組合，這些在 `setupFromId()` 直接回 `null`。
因此**編號是稀疏的：約 24% 合法**。演示頁採「即抽即驗」（隨機抽到不合法就重抽，均攤數次、毫秒級）；指定編號不合法時自動往後找最近的合法編號並說明原因。

### 兩層編號（定案 2026-07-25）

Chess960 的 SP 編號是密集的 0–959，cc960 的原始編號則是稀疏的。**不把完整版改成密集編號**，改採分工：

| 層 | 用途 | 形式 |
|----|------|------|
| **原始編號**（稀疏） | 程式、資料交換、引擎批跑 | `0 .. RAW_TOTAL−1`，約 24% 合法 |
| **密集編號**（連續） | 人用：抽籤、記譜、口述、賽事公告 | 各**小池**載入時全枚舉後給 `#1..#N`（軸對稱版 #1–#146、輕量版 #1–#216） |

不對完整版做密集編號的理由：建密集索引必須先枚舉 1,389,312 個編號（約 22 秒），與「單檔、可離線、開頁即用」的演示頁約束衝突；而人真正需要口述編號的場景（賽事抽籤）用的是小池，該處密集編號已經成立。

**盤面的字串表示**：隨機性橫跨三排，單行字串裝不下，故不另創格式——直接用象棋 FEN 的**紅方三行**，黑方由點對稱推出。標準開局為 `RNBAKABNR / .C.....C. / P.P.P.P.P`（底線／宮頂線／兵線）。完整 FEN 輸出（`toFen()`）尚未實作，是引擎審局的前置技術債。

**標準開局 ＝ 編號 3872**：象位組 0（c1,g1）、馬 {b,h}（hIdx 3）、車 {a,i}（rIdx 0）、炮 {b,h}（cIdx 13）、兵全原位 → `(3×36+13)×32 = 3872`。

## 4. 三種局面池

| 池 | 定義 | 局數 | 標準開局位置 |
|----|------|------|-------------|
| **完整版** | 全部通過檢定的局面 | **339,484** | 編號 3872 |
| **軸對稱版** | 完整版 ＋「每方自身以中線（e 路）左右對稱」 | **146** | 密集編號 #21 |
| **輕量版** | 完整版 ＋「象固定 c1/g1、兵全原位」（只隨機車馬炮） | **216** | 密集編號 #122 |

- 軸對稱版：象取對稱點對、馬車炮取對稱路對、兵進格 a=i 且 c=g 且中兵獨立（8 種兵形）。此時黑方「旋轉 180°」與「左右翻面」結果相同，棋形如標準棋端正，適合新手與展示。448 個對稱候選經檢定存留 146。
- 輕量版：216 個候選**全數合法**（點對稱使互襲自平衡，見 rationale §「為何點對稱使池子大增」），編號連續好記，適合當比賽用池。
- 軸對稱版與輕量版局數少，演示頁載入時全枚舉並給密集編號（`#1..#N`）；完整版沿用原始編號。

**兵全原位子集**（`id % 32 === 0`，象／馬／車／炮仍隨機）：**33,236** 局，占完整池 9.79%，合法率 76.6%。
不另設為第四個池——輕量版已占住「兵全原位」的競賽需求，而此子集的紅方首著機動力（avg 36.9）與完整池（avg 36.7）幾乎相同，多一個選單項目換不到實質差異。保留此數字作為「兵可否進一格」的決策依據（見 §9）。

## 6. API 參考

### `src/rules.js`（走法引擎；與隨機開局無關）

| 匯出 | 說明 |
|------|------|
| `RED, BLACK, VAL` | 常數 |
| `emptyBoard()` | 10×9 全 null 棋盤 |
| `pseudoMoves(bd, r, c)` | 該子的偽合法走法（不驗自將） |
| `isAttacked(bd, tr, tc, color)` | color 方是否攻擊該格（不含照面） |
| `kingsFacing(bd)` / `inCheck(bd, color)` | 照面 / 被將（含照面） |
| `makeMove(bd, r, c, rr, cc)` | 回傳**新棋盤**（不 mutate） |
| `legalMoves(bd, color)` | 全部合法著法 |
| `pairs(arr)` / `C_PAIRS` | 組合工具（編號系統用） |

### `src/setup.js`（隨機開局）

| 匯出 | 說明 |
|------|------|
| `RAW_TOTAL` | 編號空間 1,389,312 |
| `STANDARD_ID` | 標準開局編號 3872 |
| `decodeId(id)` | → `{ ePts, hFiles, rFiles, cFiles, pMask }`，越界回 `null` |
| `setupFromId(id)` | → 棋盤；結構衝突回 `null` |
| `quietStartCheck(bd)` | → `{ ok, why?, detail? }` |
| `checkId(id)` | 一站式：結構 ＋ 檢定 |
| `legalCaptures(bd, side)` | 只生吃子著法（檢定用的快路徑） |
| `liteCandidates()` / `symCandidates()` | 輕量版 / 軸對稱版候選編號（未過檢定，需自行 filter） |
| `E_POINTS, E_PAIRS, GROUPS, OFFSETS` | 編號系統內部結構（除錯用） |

`src/setup.js` 在 Node 下 `require('./rules.js')` 並注入 `globalThis`；在瀏覽器則靠兩份 `<script>` 共享全域詞法環境。**改動載入方式時兩種環境都要驗**（`npm run count` 走 Node、`npm test` 走 jsdom）。

## 8. 已知限制

- **檢定只看一步**：靜態互算不排除個別局面有兩步以上的開局戰術破綻。
- **「對稱可回應」容許互襲局面**：雙方各吃一子的亂戰雖對稱公平，先手主導權較大；正式競賽池建議用引擎複核（Roadmap 1）。
- **長打判例未實作**：演示頁沒有長將／長捉禁著判定，也沒有自然限著與循環同型判和。
- **先手優勢分布未量測**：Chess960 的經驗是各局面優勢不均（白方全數有利，+0.30±）；本變體預期類似，尚未用引擎驗證。緩解手段（同輪同局面、雙局換色、引擎審局池）見 rationale。
- **編號稀疏**：完整版約 24% 合法，指定編號時需自動尋近；輕量版無此問題。

## 9. v4 研究方向

1. **將位隨機**：點對稱下「將在側路必照面」的限制消失（紅將 d ↔ 黑將 f，不同路），架構上已可行。
2. 士的宮內異位（同樣按「預走合法步」原則）。
3. 馬、車、炮的「預走化」（允許已走一步的位置）。
4. 檢定改用引擎靜態評估取代價值表比大小。

> ⚠ **引擎相容性是 v4 的硬約束**：Pikafish 讀 FEN 時會依兵種驗證擺放位置（`ValidBB`），不合法直接回 `Unsupported position.`。其合法區與 v3 的擺法規則**恰好完全吻合**——象限那 7 個原軌道點、兵限 a/c/e/g/i 五路的 row 3/4、士限九宮 5 斜點、將限九宮——所以 v3 的 339,484 個局面理論上全部餵得進去。但 **v4 若讓士離開那 5 個斜點、或讓兵改路，Pikafish 會直接拒收該 FEN**，引擎審局路線當場斷掉（將位隨機不受影響，將仍在九宮內）。備案是改用 Fairy-Stockfish 的 `variants.ini` 自訂變體（可指定 `startFen`），代價是評估精度低於 Pikafish 的 NNUE。
> 以上為原始碼靜態比對的結論，**尚未實跑引擎驗證**。

## 10. 已評估並否決的方向（定案 2026-07-25，不再重開）

| 方向 | 裁決 | 依據 |
|------|------|------|
| **紅黑兩邊完全不對稱** | ❌ 否決 | ① 公平性從「可證明」退化為「只能逐局實測」——現行架構下唯一的不對稱就是「紅先走」，與標準象棋同；② 池規模變成 339,484² ≈ 1.15×10¹¹，編號、枚舉、引擎審局全部失效；③ 失去「雙方從各自座位看陣形一模一樣」這個對棋手最有力的說法 |
| **改回紅黑軸對稱為主規格** | ❌ 否決（保留為衍生池） | 軸對稱下雙方強翼同路正面相對，最省力的下法就是硬碰硬兌子——正好走回和棋軌道；點對稱使強翼錯開，天然形成兩翼互攻。且軸對稱僅 146 局。軸對稱版保留為「新手／展示池」 |
| **兵卒固定原位（不可進一格）** | ❌ 否決（保留為子集） | 池從 339,484 降至 **33,236**（−90%），但真正的理由是反面的：完整池 345,852 個 free-capture 淘汰中，兵全原位子集只占 310 個——**進兵正是絕大多數失衡局面與絕大多數結構多樣性的共同來源**。砍掉它會同時砍掉多樣性；90.2% 的合法局面含進兵，砍掉等於改變這個變體的常態面貌 |
| **完整版改用密集編號** | ❌ 否決 | 見 §3「兩層編號」：與單檔離線頁的約束衝突，且人用場景已由小池的密集編號覆蓋 |
