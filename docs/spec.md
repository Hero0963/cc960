## 0. 座標系與資料結構

| 項目 | 定義 |
|------|------|
| `col` | 0..8，紅方視角左→右，對應直線 **a..i** |
| `row` | 0..9，**row 0 = 紅方底線**，row 9 = 黑方底線；row 4/5 之間為河界 |
| 位置寫法 | 本檔用 `c1` 表示 col=c(2)、row=0（棋手習慣的 1-based 橫線編號）；程式內一律 `[row, col]` 0-based |
| 棋盤 | `bd[row][col]`，空點為 `null` |
| 棋子 | `{ t, c }`，`t ∈ K A B N R C P`（將士象馬車炮兵），`c ∈ 0 紅 / 1 黑` |
| 著法 | `[r, c, rr, cc]`（從 → 到） |

九宮：col 3..5，紅 row 0..2 / 黑 row 7..9。宮頂線＝紅 row 2 / 黑 row 7（炮的原始橫線）。河沿＝紅 row 4 / 黑 row 5。

子力價值（**僅供靜置檢定比較大小**，不是引擎評估值）：`R 9 > C 4.5 > N 4 > B 2 = A 2 > P 1`（`K 1000`）。

## 1. 擺法規則（6 條）

1. **走法、吃法、將軍、勝負規則完全同標準中國象棋**，只有初始擺放不同。
2. **紅黑點對稱**：黑方擺法 ＝ 紅方旋轉 180°，即紅方 `(r, c)` 的子，黑方對應在 `(9−r, 8−c)`。
   從各自座位看，雙方陣形一模一樣（紅「一路」兵進 ↔ 黑「1路」卒進，**不是同一 column**）。
3. **將帥固定中路九宮底線（e1/e10），雙士固定貼於兩側（d1/f1）**。中路自對稱，且中路必有兵卒相隔，永不照面。
4. **象 2 子**隨機置於「原軌道」**5 點**中任 2 點：

   | 分區 | 點（紅方） | `[row, col]` |
   |------|-----------|--------------|
   | 底線 | c1, g1 | `[0,2] [0,6]` |
   | 宮頂線 | a3, e3, i3 | `[2,0] [2,4] [2,8]` |

   象若不在底線，該底線位**留空**（不補其他子）。
   > **v4 變更**：v3 另含河沿 c5, g5（`[4,2] [4,6]`），v4 拿掉。理由見下方「為何 v4 收掉河沿」。
5. **馬 2 子、車 2 子**隨機分配「剩餘的底線非九宮路」（a,b,c,g,h,i 扣掉被底線象占用者）；
   **炮 2 子**隨機置於宮頂線任 2 路（9 路取 2），**不可疊上宮頂線的象**。
6. **兵 5 子**在 a,c,e,g,i 五路，各路獨立取「原位（row 3）」或「前進一格（row 4）」。
   （v3 另有「不可疊上河沿的象」，v4 收掉河沿象後此條自然消失——**兵的 32 種形態在任何象位下都成立**。）

### 設計原則：「預走合法步」

象與兵的所有可能起始位置，都必須是「開局前在己方領土走**原本合法步**」可以到達的點。
變的是出發陣形，不變的是每個子的本性——因此棋味、手筋與殘局知識完整保留。
（象走田字且不過河 → 從 c1/g1 出發可達的己方點共 7 個，v4 只取其中不過河沿的 5 個；兵只能直進 → 原位或進一格。）

> 注意：此原則**只約束象與兵**。馬、車在底線的重排、炮在宮頂線的重排是 **Chess960 式的同線洗牌**——車與炮的橫移剛好也是它們的合法走法，但馬從 b1 一步走不到 c1，並不符合「預走一步」。馬車炮的「預走化」列在 §10。

### 為何 v4 收掉河沿（c5/g5）

| 面向 | 結論（皆為實測） |
|------|------|
| 平衡性 | **沒有改善**：排除結構衝突後的合法率 v3 49.4% → v4 49.4%，一模一樣。河沿象不是失衡來源（失衡主要來自進兵，見 §11） |
| 棋形直觀 | **改善**：留下的 a3/e3/i3 正是「相三進五」「相三進一」的落點；拿掉的 c5/g5 是河頭象，實戰極罕見 |
| 池規模 | **代價**：合法開局 339,484 → 172,848（−49%） |
| 編號空間 | 1,389,312 → 525,312（−62%），全空間枚舉從約 19 秒降到約 10 秒 |
| 既有成果 | **全數保住**：標準開局仍為編號 3872、輕量版仍為 216 局、平衡版 70 局全數仍合法（三者都落在象位組 0，而 c1/g1 仍是 `E_POINTS` 前兩點 → `OFFSETS[0] = 0` 與組 0 內部結構皆不變） |

**決策**：以「棋形更貼近棋手直觀」為主要理由採用；**不宣稱它改善了平衡性**。

## 2. 首著靜置檢定

擺法合法只是必要條件，還要通過檢定才進入合法池。目的：**剔除「開局就有一方能白吃大子」的失衡局面**。

```
若 開局照面 或 任一方開局被將  → 不合法（why: facing / check）
對 雙方 的每個「合法的首著吃子」(r,c)→(rr,cc)：
    有根且不虧 ＝ 吃完後該格會被對方攻擊，且 VAL[被吃子] ≤ VAL[出手子]
    對稱可回應 ＝ 吃完後，對方在點對稱位置 (9−r,8−c)→(9−rr,8−cc) 仍能走同型子吃回同型子
                   （且該著不自將）
    若 兩者皆不成立 → 不合法（why: 被攻擊時 winning-capture，否則 free-capture）
全部通過 → 合法
```

**為什麼「對稱可回應」算平衡**：點對稱下紅的襲擊與黑的對應襲擊發生在**對角相反的兩處**，互不干擾——紅吃一子，黑照樣吃回同型子，淨值為零，只是把局面變尖銳而非失衡。

實作見 `src/setup.js` 的 `quietStartCheck()`。效能上只生「吃子著法」再個別驗自將（`legalCaptures()`），比全合法著法快一個量級。

## 3. 編號系統

每個開局有一個唯一整數編號（類似 Chess960 的 position number）。採**混合基數**：

```
id = OFFSETS[象位組] + ((馬idx × rBase + 車idx) × 36 + 炮idx) × 32 + 兵遮罩
```

| 欄位 | 基數 | 說明 |
|------|------|------|
| 象位組 | 10 | C(5,2)，5 個原軌道點取 2；各組大小不同，故用 `OFFSETS` 前綴和定位 |
| 馬 idx | C(m,2) | m ＝ 扣掉底線象位後、底線剩餘可用路數（4、5 或 6） |
| 車 idx | C(m−2,2) | 馬占掉 2 路後剩餘路取 2（`rBase`） |
| 炮 idx | 36 | C(9,2)，宮頂線 9 路取 2，字典序 |
| 兵遮罩 | 32 | 5 bit，bit i = 1 表示第 i 路（a,c,e,g,i）進一格 |

**編號空間**

| 象位組型態 | 組數 | m | 每組大小 | 小計 |
|-----------|------|---|---------|------|
| 兩象都在底線 {c1,g1} | 1 | 4 | 6×1×36×32 = 6,912 | 6,912 |
| 一象在底線（c/g × a3/e3/i3） | 6 | 5 | 10×3×36×32 = 34,560 | 207,360 |
| 兩象都在宮頂線（a3/e3/i3 取 2） | 3 | 6 | 15×6×36×32 = 103,680 | 311,040 |
| **合計 `RAW_TOTAL`** | 10 | | | **525,312** |

編號空間包含「結構衝突」（**炮疊上宮頂線的象**）的組合，這些在 `setupFromId()` 直接回 `null`。
v4 收掉河沿象後，「進兵疊上象」這類衝突不再存在，**兵遮罩的 32 種形態在任何象位下都合法**。
因此**編號仍是稀疏的：約 32.9% 合法**。演示頁的產生器在枚舉候選時就跳過結構衝突（不再「先生成再丟」）；指定編號不合法時自動往後找最近的合法編號並說明原因。

### 對外只用一種編號（定案 2026-08-01）

Chess960 的 SP 編號是密集的 0–959，cc960 的原始編號則是稀疏的。曾同時提供「原始編號」與各小池的密集編號（`#1..#N`），
但一個局面同時有兩三種號碼反而難懂——**產生器頁一律只顯示原始編號**。

| 層 | 用途 | 現況 |
|----|------|------|
| **原始編號**（稀疏，唯一對外編號） | 產生器頁顯示、URL 分享、程式、引擎批跑 | `0 .. RAW_TOTAL−1`，約 32.9% 合法 |
| **密集編號**（`#1..#N`） | 只在本文件內描述固定小池時偶爾使用 | 產生器頁不再顯示 |

不對完整池做密集編號的理由：建密集索引必須先枚舉 525,312 個編號（約 10 秒），與「單檔、可離線、開頁即用」的頁面約束衝突。

**盤面的字串表示 ＝ 象棋 FEN**（`toFen()`，2026-08-01 落地於 `src/setup.js`）。
標準開局為 `rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR w - - 0 1`，與公認 ground truth 逐字相符，Pikafish 零拒收。
產生器頁直接顯示 FEN 並提供複製；FEN 是唯一能跨工具（象棋軟體、引擎）交換局面的表示法。

**象棋 FEN 的四個要點**（寫錯引擎會直接拒收）：

1. 棋子字母 `K A B N R C P`，大寫紅／小寫黑——正好等於 `bd[r][c].t`，零轉換
   （另有 WXF 流派用 `E` 表象、`H` 表馬，主流引擎不吃）
2. 第一段從**黑方底線（row 9）**寫到紅方底線（row 0），每列 `col 0→8`——**不翻轉 column**
3. 走子方寫 `w`（部分中文軟體用 `r`，主流引擎不接受）
4. 六個欄位不可省；第 5 欄是無吃子半回合數，須在 `0..119`

要用外部引擎（Pikafish、Fairy-Stockfish）分析 cc960 的開局，介面就是這串文字，不需要任何綁定：
`setupFromId(id)` → 棋盤 → `toFen(bd)` → 引擎。引擎二進位請放 `engine/`（已在 `.gitignore`），不要進版控。

**分享連結**：頁面網址帶 `?id=<原始編號>`，開啟即載入該局；每次產生新局面時自動同步網址（`file://` 開啟時瀏覽器會擋 `replaceState`，此時只是不同步，其他功能不受影響）。

**標準開局 ＝ 編號 3872**：象位組 0（c1,g1）、馬 {b,h}（hIdx 3）、車 {a,i}（rIdx 0）、炮 {b,h}（cIdx 13）、兵全原位 → `(3×36+13)×32 = 3872`。

## 4. 局面池：勾選式組合（定案 2026-08-01）

不再提供「完整版／輕量版／軸對稱版／平衡版」四選一的下拉選單，改為**逐棋種勾選要不要隨機**。
不勾的棋種釘在標準開局位置：**象 c1/g1、馬 b/h、車 a/i、炮 b/h、兵全原位**。
這五個位置在任何象位組下都取得到，因此 **32 種組合每一種都必定含標準開局（3872）**。

實作在 `src/setup.js` 的 `subsetTriples` / `subsetCount` / `subsetCandidates` / `randomSubsetId`。
**候選在生成階段就跳過結構衝突**（不再「先生成再丟」）；候選數 ≤ 60,000 時全枚舉並顯示局數，超過則改「即抽即驗」。

| 勾選（隨機的棋種） | 合法局數 | 備註 |
|----|------|------|
| 全不勾 | 1 | 只有標準開局 |
| 兵 | 16 | 中兵一進就被白吃，32 種兵形只存活一半 |
| 炮 | 36 | |
| 馬、車、炮 | **216** | 全數合法；**這 216 局已被引擎全跑過**，其中 70 局入選平衡池（§8.3） |
| 象、馬、車、炮 | **10,803** | ＝「兵全原位子集」（`id % 32 === 0`），占完整池 6.25%、合法率 65.8% |
| 全勾 | **172,848** | 完整池；即抽即驗 |

其餘 26 種組合的局數由 `subsetCandidates()` 現算，不另列表。

> **舊名對照**（`liteCandidates()` 與本文件他處仍在用）：「**輕量版**」＝「只隨機馬車炮」那 216 局；「**完整版**」＝全勾的 172,848 局。

**退化的組合**：底線非九宮路只有 6 條，象占掉 2 條後只剩 4 條給馬與車。
因此在「象釘 c1/g1、車釘 a/i」時，底線只剩 b/h 給馬——**勾「馬」也沒有別的位置可選**。
同理「馬＋炮」等同「只勾炮」、「車＋兵」等同「只勾兵」。這是規則的必然，不是缺陷；
產生器頁會在該棋種後面標「**（此設定下無可選位置）**」，避免使用者以為壞掉。

### 仍保留在程式與文件中的兩個具名子池

| 子池 | 定義 | 局數 | 標準開局位置 | 產生器頁 |
|----|------|------|------|------|
| **引擎驗證平衡池** | 所有經 depth 40 實測、分數 ≤ 50 者（**實測名單**，見 §8.3） | **351** | 在池內 | ✅ 「只給引擎驗證過的平衡盤面」勾選 |
| **軸對稱版** | 完整池 ＋「每方自身以中線（e 路）左右對稱」 | **100** | #21 | 不再有入口，`symCandidates()` 保留 |

（平衡池與棋種勾選取交集：全勾時 351 局，只勾馬車炮時 94 局。）

- 這兩者都不是棋種勾選表達得出來的：平衡池是引擎實測名單，軸對稱是跨棋種的對稱約束。平衡池已於 2026-08-01 以獨立勾選回到介面；軸對稱版仍只有資料、沒有入口。
- 軸對稱版：象取對稱點對、馬車炮取對稱路對、兵進格 a=i 且 c=g 且中兵獨立（8 種兵形）。此時黑方「旋轉 180°」與「左右翻面」結果相同，棋形如標準棋端正。v4 起象的對稱點對只剩 {c1,g1}{a3,i3} 兩組（v3 有三組），候選 448 → 320，經檢定存留 100。
- 引擎驗證平衡池：v4 改動後 351 局**全數仍合法**（`npm run count` 有此檢查）。

| `BALANCED_CP` | 原始資料：`[原始編號, 分數]` 對，351 筆 |
| `E_POINTS, E_PAIRS, GROUPS, OFFSETS` | 編號系統內部結構（除錯用） |

`sel` 的形狀是 `{ e, n, r, c, p }`（象／馬／車／炮／兵），值為布林：`true` ＝ 隨機、`false` ＝ 釘在標準開局位置。

`src/setup.js` 在 Node 下 `require('./rules.js')` 並注入 `globalThis`；在瀏覽器則靠兩份 `<script>` 共享全域詞法環境。**改動載入方式時兩種環境都要驗**（`npm run count` 走 Node、`npm test` 走 jsdom）。

## 8. 引擎審局與平衡版（2026-07-25 實測）

### 8.1 方法

| 項目 | 值 |
|------|-----|
| 引擎 | **Pikafish 2026-01-02**（UCI／NNUE，`pikafish-avx512`） |
| 搜尋預算 | **`go depth 40`** |
| 設定 | `Threads=1`（保證決定性）、`Hash=1024`、`MultiPV=1`、`UCI_ShowWDL=true` |
| 樣本 | **輕量版 216 局全跑**（非抽樣），零錯誤 |
| 局面表示 | 象棋 FEN，紅方先行（`… w - - 0 1`） |

分數是**正規化後的 centipawn**：現代引擎的評估已校準到勝率，**不是材料值**。實測（Pikafish depth 30，從標準開局改材料）：標準開局 21 分、多一個兵 35 分、多一個馬 **339** 分、多一個車 **581** 分——一個兵只值約 14 分，一個馬值 318 分。完整換算表見 [project-guide.md §5](project-guide.md)。

**點對稱校準檢定**（cc960 特有）：局面紅黑點對稱，故「紅先」與「黑先」在賽局上同構；UCI 的 `score` 相對走子方，兩者理應相同。實測 11 個局面的差距**中位數 5 分、最大 14**，而訊號範圍是 18–485 —— 引擎並不知道局面對稱，卻算得幾乎一致，可作為「NNUE 對非標準開局仍自洽」的內部證據。

### 8.2 分布

```
n=216   min 12 ｜ P10 24 ｜ P25 36 ｜ 中位 69 ｜ P75 170 ｜ P90 262 ｜ max 485
        平均 115 ｜ 標準差 101
```

| 對照 | 平均 | 標準差 | 最大 |
|------|------|--------|------|
| **cc960 輕量版** | **115** | **101** | **485** |
| Chess960 全 960 局（Stockfish 17.1 / depth 30） | 33 | 12 | 81 |
| 標準象棋開局（編號 3872） | 18 | — | — |

**離散度是 Chess960 的 8.4 倍。** 推測與象棋開局的炮、車射程未被兵牆封閉有關——西洋棋的初始陣形被完整兵列擋住，象棋的兵只占 5 路。**隨機開局在象棋比在西洋棋更需要平衡篩選。**

標準開局的 18 分在 216 局中排第 8 平衡——它本身就是個很平衡的局面。

**所有實測局面的分數都是正的**：766 筆紀錄中沒有任何一筆 ≤ 0，最小值 +5。**紅方（先手）在每個局面都至少略優**，與 Chess960「960 局全數利白」的發現一致。

### 8.3 引擎驗證過的平衡開局（351 局）

**定義：所有經 depth 40 實測、紅方先手優勢 ≤ 50 分的局面，共 351 局**（含標準開局）。
編號與分數硬編於 `src/setup.js` 的 `BALANCED_CP`（`[原始編號, 分數]` 對），由 `balancedCandidates()`／`balancedEval(id)` 匯出。
閾值 2026-08-01 由 40 放寬到 50（280 → 351 局）：50 分的局面紅方勝率仍只有 14.8%，放寬 10 分換到 25% 的池子。

資料來自兩批批跑，設定相同（depth 40／`Threads=1`／`Hash=1024`／`MultiPV=1`）故可併表：

| 批次 | 樣本 | 實測局數 |
|------|------|---------|
| 2026-07-25 | 「只隨機馬車炮」216 局**全跑** | 216 |
| 2026-08-01 | 32 種勾選組合各取樣 min(25, N) | 454（與上批重疊 53） |
| **合計（去重）** | | **617**，其中 **351** 局分數 ≤ 50 |

| 指標 | 值 |
|------|-----|
| 平衡局數 | **280** |
| 評估範圍 | 5–40 分 |
| **32 種勾選組合每一組都有平衡局** | 最少 1 局（退化組合），最多 280 局（全勾） |
| 其中屬「只隨機馬車炮」者 | **70**（即 2026-07-25 的原始平衡版） |
| 最佳著與第三選擇的分差（70 局子集實測） | 1–26 分（**中位 10**） |

分差中位數只有 10 分，代表這些局面**沒有唯一解、可行下法多**——這正是本變體要的：讓棋手靠棋力選擇，而不是背譜。

**產生器頁的用法**：勾「只給引擎驗證過的平衡盤面」，池就變成這 280 局與目前棋種勾選的**交集**（全勾時即全部 280 局，只勾馬車炮時退回原本那 70 局）。
另外，只要目前局面在這 280 局內，「這一局」面板就會顯示它的實測評估值。

⚠ **`BALANCED_CP` 是實測結果，不是推導出來的。** 只要擺法規則或首著檢定有任何改動，這張表就失效，必須重新評估（`npm run count` 只驗它們仍合法，驗不出評估值是否還成立）。
v4 改動後 280 局全數仍合法；評估值未重測，但 v4 只拿掉河沿象位，而這些局面的象都不在河沿，盤面一格未動。
⚠ **這 280 局是「已知平衡」，不是「全部平衡」**——完整池 172,848 局中只有 617 局被實測過，其餘未知。

### 8.4 勾選組合的平衡率地圖（2026-08-01 實測）

32 種勾選組合各取樣 `min(25, N)` 局（等距抽樣），去重 454 局跑同一組設定（depth 40／Hash 1024／MultiPV 1）。

**主結論：失衡的主因是「馬和車同時隨機」，不是進兵。**

| 條件 | n | 平衡率（\|cp\| ≤ 40） | 95% CI | cp 中位 |
|------|---|--------|--------|---------|
| **馬與車都隨機** | 181 | **28%** | 22–35% | **74** |
| **馬車未同時隨機** | 486 | **71%** | 67–75% | **31** |
| 兵隨機 | 373 | 54% | 49–59% | 39 |
| 兵固定 | 294 | 67% | 61–72% | 33 |
| 象隨機 | 385 | 58% | 53–62% | 37 |
| 炮隨機 | 400 | 58% | 53–63% | 36 |

進一步拆解「馬車都隨機」的 171 筆樣本，找到**單一結構因子**：

| 條件 | n | 平衡率 | 95% CI | cp 中位 |
|------|---|--------|--------|---------|
| 車有落在 **b 或 h 路** | 129 | **16%** | 11–24% | **95** |
| 車不在 b/h | 42 | **62%** | 47–75% | **32** |

b/h 是炮的原始路——車一落到 b/h 就站在自家炮的正下方，形成車炮同線的強襲陣。
`quietStartCheck()` 只看一步吃子，攔不住這種**陣形性**優勢（呼應 §9 的「檢定只看一步」）。
標準開局的車在 a/i，不受此條影響。

**建議勾法**（池大小 × 平衡率的取捨）：

| 用途 | 勾選 | 池大小 | 平衡率 |
|------|------|-------|-------|
| 日常對局（建議預設） | 象、炮、兵 | 4,272 | 60% |
| 最多變化 | 象、車、炮、兵 | 14,592 | 48% |
| 幾乎必平衡 | 象、兵 | 160 | 92% |
| 正式比賽 | §8.3 的 70 局名單 | 70 | 依定義 |

⚠ **限制**：n=25 的信賴區間很寬，除了「馬車」與「車落 b/h」兩條聚合結論，單組之間的排序（如 48% vs 52%）**不具統計意義**。
抽樣估計回答的是「隨機抽一局有多大機率平衡」，**不等於可用的平衡名單**——後者要跑該組合的全池。

## 9. 已知限制

- **檢定只看一步**：靜態互算不排除個別局面有兩步以上的開局戰術破綻。
- **「對稱可回應」容許互襲局面**：雙方各吃一子的亂戰雖對稱公平，先手主導權較大；正式競賽池建議用引擎複核（Roadmap 1）。
- **長打判例未實作**：演示頁沒有長將／長捉禁著判定，也沒有自然限著與循環同型判和。
- **先手優勢分布未量測**：Chess960 的經驗是各局面優勢不均（白方全數有利，+0.30±）；本變體預期類似，尚未用引擎驗證。緩解手段（同輪同局面、雙局換色、引擎審局池）見 rationale。
- **編號稀疏**：完整版約 32.9% 合法（唯一的結構衝突是炮疊上宮頂線的象），指定編號時需自動尋近；輕量版無此問題。

## 10. v5 研究方向

1. **將位隨機**：點對稱下「將在側路必照面」的限制消失（紅將 d ↔ 黑將 f，不同路），架構上已可行。
2. **士的宮內異位**（同樣按「預走合法步」原則）：士從 d1/f1 走斜步可達的己方點正好是九宮 5 斜點 `{d1, f1, e2, d3, f3}`，取 2 ＝ **10 種**。
   可**向後相容**地加成最高位基數（`id = 士idx × 525,312 + 舊id`，士idx=0 ＝ d1/f1），如此標準開局仍為 3872、平衡版名單不失效。
   代價：`RAW_TOTAL` ×10；新增一種結構衝突（士在 d3/f3 撞上宮頂線 d/f 路的炮）。
3. 馬、車、炮的「預走化」（允許已走一步的位置）。
4. 檢定改用引擎靜態評估取代價值表比大小。

> ⚠ **引擎相容性是後續版本的硬約束**：Pikafish 讀 FEN 時會依兵種驗證擺放位置（`ValidBB`），不合法直接回 `Unsupported position.`。其合法區**涵蓋** v4 的擺法規則——`ValidBB` 允許象在那 7 個原軌道點（v4 只用其中 5 點，是它的子集）、兵在 a/c/e/g/i 五路的 row 3/4、**士在九宮 5 斜點**、將在九宮——所以 v4 的 172,848 個局面理論上全部餵得進去。
> 因此上列第 1、2 項（將位隨機、士在 5 斜點內異位）**都在 Pikafish 的合法區內，不會被拒收**；真正會踩線的是「讓士離開那 5 個斜點」或「讓兵改路」。備案是改用 Fairy-Stockfish 的 `variants.ini` 自訂變體（可指定 `startFen`），代價是評估精度低於 Pikafish 的 NNUE。
> 以上為原始碼靜態比對的結論，**尚未實跑引擎驗證**。

## 12. 程式架構

> 原 `docs/architecture.md`，2026-08-01 併入本檔（兩份文件的讀者是同一群人，且 §6 API 參考與模組說明高度重疊）。

### 12.1 心智模型

整個專案只有 **677 行 JavaScript**，零執行期相依。一句話：

> **一副普通的象棋引擎（`rules.js`）＋ 一個「把整數編號變成開局擺法」的產生器（`setup.js`）。**

這兩者是**單向相依**的：`setup.js` 用 `rules.js`，反過來絕對不行。
`rules.js` 完全不知道「隨機開局」這回事——它就是一副標準象棋，換掉起始盤面照樣運作。
**這個分界是整個設計的地基**，破壞它等於讓走法引擎與變體規則糾纏在一起。

```
                       ┌─────────────────────────────┐
  展示層                │ shell.html  外殼：HTML/CSS/文案 │
                       │ ui.js       SVG 棋盤、勾選式產生 │
                       └──────────────┬──────────────┘
                                      │ 只呼叫全域函式
                       ┌──────────────▼──────────────┐
  變體層                │ setup.js                     │
                       │  編號系統 ＋ 擺位產生 ＋ 首著檢定 │
                       └──────────────┬──────────────┘
                                      │ 單向相依（反向 import 一律拒絕）
                       ┌──────────────▼──────────────┐
  規則層                │ rules.js                     │
                       │  走法／吃法／將軍／合法著法      │
                       └─────────────────────────────┘

  工具（不參與執行期）：scripts/build.js  scripts/count.js  scripts/stats.js  test/test-dom.js
```

### 12.2 各檔重點（函式清單見 §6 API 參考）

| 檔案 | 行數 | 重點 |
|------|-----|------|
| `src/rules.js` | 169 | `pseudoMoves()` 是最大的一支（約 68 行）：蹩馬腿、塞象眼、炮的隔子吃、兵過河橫走、士象不出界都在裡面。`VAL` **只用於首著檢定比大小**，不是引擎評估值 |
| `src/setup.js` | 315 | 編號系統（§3）、首著檢定（§2）、勾選式產生器（§4）、`toFen()`。`legalCaptures()` 是刻意的快路徑——只生吃子著法再個別驗自將，比全合法著法快一個量級，全枚舉 52 萬局時是效能關鍵 |
| `src/ui.js` | 193 | 包在一個 IIFE 裡，只呼叫全域函式，沒有 import。**不提供行棋**——頁面只生成開局 |
| `src/shell.html` | 166 | HTML／CSS／文案。三個注入點 `/*__RULES__*/`、`/*__SETUP__*/`、`/*__UI__*/` 是純註解，`build.js` 換成 js 內容 |

**`src/ui.js` 的關鍵設計**

| 函式 | 說明 |
|---------|------|
| `poolFor(sel)` | 勾選組合 → 合法編號清單；候選 > `ENUM_LIMIT`（60,000）回 `null` 表示改即抽即驗。以 `poolCache` 依組合鍵快取 |
| `balancedPoolFor(sel)` | 平衡池 280 局 ∩ 目前棋種勾選（全勾 280、只勾馬車炮 70）；快取鍵前綴 `B` |
| `renderPoolNote()` | 用 `subsetCount` 比對「把某軸改成固定後筆數變不變」，把**勾了卻無可選位置**的軸標出來 |
| `copyText()` | `navigator.clipboard` 不可用時退回隱藏 textarea ＋ `execCommand` |

**版面常數**：`CELL = 54`、`MARGIN = 34`；`X(c) = MARGIN + c*CELL`、`Y(r) = MARGIN + (9-r)*CELL`
（**注意 Y 是反的**：`row 0` 是紅方底線，畫在畫面下方。）

**狀態**：單一物件 `S`（`id` ＝ 目前編號、`sel` ＝ 棋種勾選、`onlyBalanced` ＝ 是否只給平衡盤面）。盤面不存在 `S` 裡，每次由 `setupFromId(S.id)` 現算。

**`file://` 的兩個坑**：`history.replaceState` 會被擋（來源為 null）、`navigator.clipboard` 不存在。兩處都要有 fallback——產生器必須能離線直接開。

### 12.3 兩種執行環境（改載入方式時兩邊都要驗）

同一份 `setup.js` 要能在兩個環境跑：

- **Node**：`require('./rules.js')` 並把結果注入 `globalThis`
- **瀏覽器**：兩份 `<script>` 本來就共享全域詞法環境，不需要 import

所以 `rules.js` 的匯出寫成條件式（`if (typeof module !== 'undefined') module.exports = {...}`）。
**驗證方式**：`npm run count` 走 Node、`npm test` 走 jsdom，**兩個都跑過才算數**。

### 12.4 測試的關鍵設計

`test/test-dom.js` 用 jsdom 載入的是 **`docs/index.html`（建置後的成品）**，不是原始碼：

```js
const dom = new JSDOM(html, { url: BASE, runScripts: 'dangerously', pretendToBeVisual: true });
```

**所以組裝流程壞掉也會被抓到**——注入點改名、`</style>` 切點跑掉，測試都會紅。
測試方式是**模擬真實互動**（派發 click 與 change 事件），不是直接呼叫內部函式。
`url` 一定要給（不能用預設的 `about:blank`），否則 `history.replaceState` 與 `?id=` 相關的項目測不到。

### 12.5 不可破壞的不變量

| 不變量 | 怎麼驗 |
|--------|--------|
| `rules.js` 不得依賴 `setup.js` | 程式碼審查；反向 import 一律拒絕 |
| 紅黑點對稱：黑 `(9−r, 8−c)` 與紅 `(r,c)` 同型異色 | `npm run count` 的「點對稱抽驗違反格數 = 0」 |
| 標準開局在合法池內、編號 3872、紅方 44 著 | `npm run count` 前三行 |
| 走法引擎行為（蹩腿、塞眼、照面、隔子吃、過河橫走） | `npm run count`：引擎一被改壞，172,848／216／100／280／44 這些期望值立刻不對 |
| 32 種勾選組合每一種都含標準開局 | `npm test` |
| `BALANCED_CP` 是引擎實測名單 | 改擺法規則或檢定後**必須重跑引擎評估**；`npm run count` 只驗它們仍合法 |
| `makeMove()` 不 mutate 傳入盤面 | 沿用慣例；改動時特別小心 |
| `docs/index.html` 是建置產物 | **永遠不要手改**，只能由 `npm run build` 產生 |
| 產生器頁單檔、零相依、可離線 | GitHub Pages 直接吃 `docs/index.html`；不引入框架或 bundler |
